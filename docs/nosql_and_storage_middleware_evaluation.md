# 非关系型数据库 (NoSQL) 与扩展中间件完整盘点及必要性评估

> **文档版本**：v1.0.0  
> **制定日期**：2026-11-19  
> **核心议题**：当前架构还缺失其他必需中间件吗？是否需要引入 MongoDB、对象存储 (MinIO) 或其他 NoSQL？  
> **核心结论**：  
> - **当前基础架构已形成闭环**：`MySQL 8.0`（关系型） + `Redis 7.2`（键值 NoSQL） + `RabbitMQ`（消息解耦） + `Loki`（日志流）已完全覆盖常规微服务的基础诉求。  
> - **两大按需高频补充建议（强烈建议按业务评估）**：  
>   1. **若有文件/图片/视频/安装包上传**：👉 **必须引入 MinIO (私有 S3 对象存储，~150MB)**，彻底解决容器多副本文件丢失与共享难题；  
>   2. **若有游戏背包/玩家角色存档/灵活动态属性**：👉 **建议补充 MongoDB 7.0 (文档型 NoSQL，~300MB)**，天然 Schema-free 免除频繁 ALTER TABLE。

## 一、 当前数据与通信中间件现状梳理

目前已规划的基础设施：
- **MySQL 8.0**：负责强事务、账户资产、订单等高度规整的关系型数据存储；
- **Redis 7.2**：本身就是最经典的 **Key-Value 非关系型数据库 (NoSQL)**，负责高速缓存、分布式锁、计数器、用户 Session 会话；
- **RabbitMQ 3.13**：负责异步削峰、跨服务解耦通知、延迟取消任务；
- **Grafana Loki**：专职负责轻量化海量日志时序文本流存储。

## 二、 常见 NoSQL 非关系型数据库盘点与业务匹配度

| NoSQL 类型 | 典型代表 | 核心业务场景 | 相比现有组件的优势 | 对本项目的必要性评级 | 单机内存开销 |
|---|---|---|---|---|---|
| **1. 对象存储 (S3 协议)** | **MinIO** | 用户头像、视频文件、游戏资源包、Excel 报表导出、备份文件 | **避免容器本地存储陷阱**：在 K8s/微服务中，容器重启本地文件即丢失，且多副本无法共享。MinIO 提供生产级 S3 API 存储。 | ⭐⭐⭐⭐⭐<br>**(有文件上传则为必选)** | **超低**<br>(~150MB，自带 Web 后台) |
| **2. 文档型 NoSQL** | **MongoDB 7.0** | 游戏角色属性、道具背包、嵌套 JSON 数据、动态表单配置 | **免除频繁加列**：支持极其灵活的深层嵌套文档结构，BSON 高效读写，比在 MySQL 存 JSON 字段更易建索引和聚合查询。 | ⭐⭐⭐⭐<br>**(游戏/复杂文档推荐)** | **中等**<br>(~250MB ~ 350MB) |
| **3. 搜索引擎 NoSQL** | **Elasticsearch / Meilisearch** | 电商商品全文检索、大文本分词检索、玩家昵称纠错搜索 | 倒排索引支持毫秒级全文复杂模糊搜索。 | ⭐⭐<br>**(纯管理系统非必需)** | ES 较重 (~1GB+)<br>Meili 极轻 (~100MB) |
| **4. 时序型 NoSQL** | **VictoriaMetrics / InfluxDB** | 硬件指标监控、高频传感器数据 | 高压缩比时序存储。 | ⭐⭐⭐<br>**(监控已覆盖)** | 监控栈中已有 Prometheus 覆盖 |
| **5. 列式 / 宽表 NoSQL** | **ClickHouse / HBase** | 亿级用户行为明细、复杂 OLAP 实时数仓分析 | 大宽表高压缩比，海量数据聚合统计秒级出结果。 | ⭐⭐<br>**(大数据专门分析才需要)** | 较高 (~1GB+) |

## 三、 两大高价值推荐补充方案深度解析

### 1. 为什么“对象存储 (MinIO)”在微服务中近乎刚需？
在单体传统项目中，开发者习惯直接把文件存在服务器的 `/var/www/uploads` 目录。  
但在**容器化与微服务架构**下，这种做法是绝对禁止的：
- **容器无状态原则**：容器销毁重建，本地文件灰飞烟灭；
- **多副本负载均衡**：用户把图片上传到了 Pod A，下次请求被网关分流到了 Pod B，Pod B 本地根本没有这个文件，直接报 404！
- **生产同构标准**：
  - 本地部署单容器 **MinIO**（开放 9000 API 端口，9001 Web 控制台端口）；
  - 微服务后端统一使用官方标准的 AWS S3 SDK 读写文件；
  - 未来无论部署到**腾讯云（直连腾讯云 COS）**还是**阿里云（直连阿里云 OSS）**，业务代码 **1 行都不用修改**，100% 协议无缝兼容。

---

### 2. 什么时候应该引入 MongoDB？
- **场景判断**：
  - 如果项目完全是规整的企业管理后台、用户权限表、角色菜单表：👉 **MySQL 足够**。
  - 如果项目包含游戏业务、角色背包、道具属性字典、动态任务进度：
    - 比如：一个角色可能有 100 种属性，每个装备有随机词条、强化等级、镶嵌宝石；
    - 在 MySQL 里建表需要创建大量关联表，或者在单表设计几十上百个字段；
    - 在 **MongoDB** 里，一个角色就是一个 JSON 文档，随时可以新增字段，查询更新极为自然。

## 四、 宿主机资源容纳度评估与建议

如果我们将 **MinIO**（对象存储）和 **MongoDB**（文档数据库）一并纳入本地环境：

| 模块分类 | 包含组件 | 预估内存占用 |
|---|---|---|
| **已有全套基础设施** | K3s + Polaris + trpc-gateway + MySQL + Redis + RabbitMQ + 观测套件 + 双大盘 | ~4.95 GB |
| **补充组件 1 (对象存储)** | MinIO (S3 兼容对象存储，含 Web 控制台) | ~150 MB |
| **补充组件 2 (文档型 NoSQL)**| MongoDB 7.0 (带数据卷持久化) | ~300 MB |
| **全套顶配生态汇总** | **完整包含关系型、缓存、消息、对象存储、文档数据库** | **约 5.4 GB** |

> **评估结论**：宿主机 16GB 物理内存（可用 12GB），即便把 MinIO 和 MongoDB 完整加入，总开销也仅占 **5.4 GB**，宿主机依然剩余 **6.5GB+ 充裕内存**，完全在轻松承载范围内！

---

## 五、 决策建议

1. **建议直接补齐 MinIO（对象存储）**：只要业务有任何文件、图片、静态包上传导出，MinIO 是云原生微服务的通用标准，仅占 150MB，生产同构收益极大；
2. **MongoDB 按需定夺**：若业务涉及游戏道具背包、动态角色档案或非规则 JSON 文档，建议补齐；若纯结构化表单，初期可先用 MySQL 8.0 的 JSON 类型。
